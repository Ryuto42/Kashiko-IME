# kashiko-engine

Kashiko のコアライブラリ。ローマ字→ひらがな変換、llama.cpp によるニューラルかな漢字変換、辞書、学習キャッシュを提供します。

サーバー・CLIツールは [kashiko-tools](../kashiko-tools/)、IMEのステートマシンと候補生成は [kashiko-im](../kashiko-im/) を参照してください。

## モジュール

| モジュール | 役割 |
|---|---|
| `romaji` | ローマ字→ひらがな変換 |
| `kanji` | llama.cpp による GGUF 推論。変換、候補の尤度評価、ライブ変換 |
| `dict` | double-array trie 辞書（完全一致・前方一致）。テキストは平坦なアリーナに保持し、IME では mmap して使う（下記） |
| `learning` | 変換学習キャッシュ。抑制リスト（候補削除）も同じ仕組みで保持 |
| `learning_file` | 学習キャッシュの暗号化（ChaCha20-Poly1305） |
| `segment` | 変換結果を読みに整列させる文節アラインメント |
| `counter` | 数詞＋助数詞の分解 |
| `loanword` | カタカナ借用語の英語表記 |
| `latin` | 打鍵内容からの英単語復元 |
| `typo` | キーボード配置に基づく打鍵誤りの推定 |
| `kana` | かな種別の判定・変換ユーティリティ |
| `rewriter` | 記号・絵文字・全角半角・数値表記のバリアント生成 |

## 辞書のメモリ配置

辞書のテキストは1つの平坦なバッファに保持し、`u32` のオフセットで索引します。読みごとの `String` と候補ごとの `Vec<String>` を持つ素直な構造は、システム辞書の規模（約200万読み・約270万候補）では**1エントリごとに個別のヒープ確保**が必要になり、実測で196MBのファイルが382MB常駐していました。アリーナは確保が3回で済み、同じバイト列を保持して229MBです。

内訳: trie 76MB / テキスト 97MB / 読み索引 23MB / 候補索引 30MB。

読み込みはファイルをストリームしながらアリーナへ直接詰めます。ファイルは長さとスコアをテキストに挟んだ形で並んでおり、それらは索引側に持つので blob へ写す必要がありません。読み込み時間は約0.17秒です。

IME では、このアリーナをそのままの並びで書き出したキャッシュ（`dict.bin` と同じ場所の `dict.mmap`）を mmap して使います（`Dictionary::load_mapped`）。ページは引いた部分だけ読み込まれ、システムがいつでも手放せるため、プロセスのメモリ（Physical footprint）に数えられません。常駐は辞書込みで約50MBです（アリーナを読み込む場合は約280MB）。キャッシュは `make install` 時に作られ、`dict.bin` が差し替えられると（サイズか更新時刻が変わると）作り直されます。trie は yada が境界検査なしで読むため、キャッシュでも読み込み時に検証します。

なお、GGUFモデルは llama.cpp が mmap するため、ファイルサイズ分は file-backed（clean）で、メモリ圧にはなりません。

## 推論の負荷

- **ライブ変換は前回の計算を使い回します。** 推論コンテキストをキー入力の間で保持し、前回と共通するプロンプトの先頭（文脈と読みの大部分）は KV キャッシュから再利用します。さらに前回の変換結果を下書きとして一括で検証し、一致した分は1トークンずつの生成を省きます。出力は通常の貪欲生成と同一です。入力が終わる（確定・取り消し）とコンテキストを解放します。
- **ビーム探索と候補の採点も同様です。** 1回の探索・採点につきコンテキストは1つで、プロンプトは1回だけ評価し、各ビーム・各候補は差分のトークンだけを評価します。
- **Metal（GPU）は組み込みません。** 推論は CPU のみで、組み込むと起動時にシェーダのコンパイルが走るためです（`.cargo/config.toml` と `cmake/ggml-cpu-only.cmake`）。

## 候補の評価

候補の自然さを文字単位の負の対数尤度（NLL）で評価します。値が小さいほど自然で、文字数で正規化しているため長さの違う候補も比較できます。文脈にはカーソル左側の確定済みテキストを渡します（文脈込みで評価することがリスコアリングの目的なので、空にすると効果が落ちます）。

平均に加えて**最悪の1文字**も返します。平均だけでは長文を判定できず、多数の文字のうち1つが誤変換でもほとんど動かないためです。局所的な破損は局所的な指標でしか見えません。

候補リストはまとめて評価します。スコアラを1つだけ生成することで、共有プロンプトがKVキャッシュに残り候補ごとの作り直しを避けられます。

`KanaKanjiConverter` は `Send + Sync` です。推論は `&self` で呼び出しごとに自前のコンテキストを作るため、複数スレッドから同時に使えます（IMEはこれを利用してバックグラウンド探索を別スレッドで走らせます）。

## ライブ変換

1候補のgreedyデコードを行い、**モデル自身が自分の出力を不確からしいと評価したときだけ**ビーム探索で作り直します。greedyは各ステップで最善手に飛びつくため近視眼的で、ビームなら避けられる不自然な文に入り込むことがあります。

判定に使う対数確率は生成時のlogitsから得るため**追加の推論コストはゼロ**で、毎キーストロークで呼ばれる経路でも使えます。

## 学習キャッシュ

読みと確定した表層形を記録し、完全一致と前方一致（予測変換）で引けます。誤変換やスペルミスに由来する意味の取れない組み合わせと、極端に長い表層形は記録しません。

保存時は暗号化します。入力内容の記録なので、平文でディスクに残すべきものではありません。鍵はインストール時に生成してキャッシュの隣に置きます。認証付きなので改変されたファイルはエラーになり、暗号化前の平文キャッシュは読み込んで次回保存時に書き直します。詳細は [kashiko-im の README](../kashiko-im/README.md#learning-cache) を参照してください。

## モデル

`models.toml` で定義され、バリアントIDを指定すると自動的にダウンロードされます。

| バリアントID | パラメータ数 | 量子化 | 既定 |
|---|---|---|---|
| `jinen-v1-xsmall-q5` | 26M | Q5_K_M | |
| `jinen-v1-small-q5` | 90M | Q5_K_M | |
| `jinen-v2-small-q8` | 110M | Q8_0 | Yes |
| `jinen-v2-small-q5` | 110M | Q5_K_M | |
| `jinen-v2-xsmall-q5` | — | Q5_K_M | 補助 |
| `kanakanji-edge-33m-q8` | 33.5M | Q8_0 | |

既定は Q8_0 です。Apple Silicon では llama.cpp が Q8_0 の重みを CPU 向けの並びに組み替えるため、Q5_K_M より速く（ライブ変換の1キーあたり CPU 時間が約半分）、精度も同等以上です。その分メモリは約110MB多く使います。

### jinen 形式

モデルは Private Use Area の特殊Unicodeトークンを使う jinen 形式で学習されています。この形式は [zenzai](https://github.com/azooKey/AzooKeyKanaKanjiConverter/blob/main/Docs/zenzai.md) のかな漢字変換モデル zenz の第3世代（zenz-v3）フォーマットを参考にしており、同じトークン配置を採用しています。

| トークン | Unicode | 用途 |
|---|---|---|
| INPUT_START | U+EE00 | カタカナ入力開始 |
| OUTPUT_START | U+EE01 | 漢字出力開始 |
| CONTEXT | U+EE02 | 左コンテキストマーカー |

プロンプト形式: `{CONTEXT}<context>{INPUT_START}<katakana>{OUTPUT_START}`
